## 一、角色必须绑定 session 编号

| 项 | 要求 |
| --- | --- |
| 绑定 | 一个角色**绑定一个固定的 session 编号**（`S` 选了就固定下来） |
| 回答 | 这个角色**只能用这个 session** 来回答/做事，不许跑到别的 session |
| 判据 | 问某个角色时，投递只落到他绑定的那个 session；他在别的 session 里说的话，不算他的回答 |
| 界面 | 会话列表 / 角色信息窗里能看到"他绑的是哪个 session" |

## 二、无角色的 session（"无人的 session"）

| 项 | 要求 |
| --- | --- |
| 定义 | tmux / hermes 里存在、但**没有对应角色**的 session |
| 能发 | **可以发信息**（能往外说） |
| 收指令 | **可以接收指令，但只能由「经理」或「女仆」发** |
| 其他人 | **其他人无权**给这种 session 发信息（发了也不投递、要报错） |
| 判据 | ① 经理/女仆发 → 投递成功；② 其他角色发 → 被拒（返回明确原因，不是静默丢掉）；③ 这种 session 出现在会话列表里，且标注"无角色" |

## 三、看门狗（watchdog / 需要批准的东西）

| 项 | 要求 |
| --- | --- |
| 是否删除 | **不删除看门狗**（本人思虑再三：保留） |
| 去向 | 看门狗的**每一条信息都发给女仆**（`home.maid`），**由女仆转告本人**（QQ） |
| 强制范围 | **所有需要批准的东西都必须走这条路**：看门狗 → 女仆 → 本人 |
| 女仆的边界 | 女仆**不授权、不替本人做决定**，只负责把话带到、把本人的答复带回去 |
| 旧记录 | 清理掉之前堆的「授权/待批准」记录（那些是看门狗产生的），保留机制本身 |
| 判据 | ① 出现需批准项 → 女仆收到一条，且本人 QQ 收到转告；② 本人答复 → 回到发起方；③ 拿掉旧的堆积记录后，队列干净 |

## 四、消息来源必须区分得开

| 项 | 要求 |
| --- | --- |
| 问题 | 同一条消息可能既有"看门狗发给他的"，又有"聊天发给他的"，现在**看着像一条、分不出来** |
| 要求 | **来源要在同一条消息里能一眼区分**：是看门狗发的、还是聊天发的；谁发的、通过哪种方式（私聊/定向·他人可见/广播） |
| 判据 | 会话里（终端形式）每条进来的消息都带来源标签，看门狗来源用**明显不同的标记**（与聊天来源视觉上不同）；气泡里同样能看出这条是谁、从哪来的 |

## 六、工作纪律（本轮教训，适用于以上全部）

- 改前端后**必须**：`node --check` → 构建 → **从 APK 里解出 JS 再 `node --check`** + 关键标记计数，全对才出包。
